# rjtd-wasm

WebAssembly bindings for parsing and rendering Ichitaro JTD documents in
browsers.

`rjtd-wasm` is the browser binding layer of
[rjtd](https://github.com/OpenJTD/rjtd). `JtdDocument` is the canonical Rust and
viewer-facing name. Rust `HwpDocument` remains a type alias. The generated SDK
retains its existing JavaScript `HwpDocument` class; the viewer's
[`rjtd.mjs`](../../../openjtd.github.io/rjtd.mjs) entry point exports the same
constructor as `JtdDocument` and also retains `HwpDocument`. Method names and
construction limits remain unchanged. Consumer-specific APIs belong at the
[application boundary](../../../docs/ARCHITECTURE.md).

## Developer preview

Version 0.0.1 is an experimental developer preview. Rust, generated JavaScript,
and WebAssembly-facing APIs may change in any later 0.0.x release.

The source checkout may include unreleased development after the dated 0.0.1
release. See [feature status](../../../docs/FEATURE-STATUS.md) and
[validation](../../../docs/VALIDATION.md) for current scope, and the
[changelog](../../CHANGELOG.md) for the release record. The
[architecture](../../../docs/ARCHITECTURE.md) describes the optional model
rendering boundary. This wrapper explicitly enables rendering without model
bitmap decoding.

## What it provides

- `JtdDocument` construction from JTD-family bytes.
- Document and page information APIs.
- Text-first SVG/HTML rendering and viewer-facing fallback APIs.
- Search, selection, navigation, and basic editing surfaces backed by
  `rjtd-model::DocumentCore`.

The crate supplies Rust and `wasm-bindgen` exports. JavaScript glue and an npm
package are generated by downstream tools such as `wasm-pack`; publishing this
crate to crates.io does not itself publish an npm package.

## `JtdDocument` contract

`JtdDocument` wraps OpenJTD's JTD-family `DocumentCore`. The legacy Rust alias
and generated JS class retain their old spelling for existing consumers; neither
is a claim that this crate parses HWP. Rust callers use `JtdDocument::from_bytes`,
`from_bytes_with_limits`, or `from_document_with_limits`. JavaScript callers can
use `new JtdDocument(bytes)` through `rjtd.mjs`, or the existing generated SDK
`new HwpDocument(bytes)`.

`JtdDocument` implements both `Deref<Target = DocumentCore>` and `DerefMut`.
That makes the Rust-facing `DocumentCore` query, rendering, navigation, and
editing-fallback methods directly available through the wrapper. The generated
JavaScript API is limited to the explicitly exported `wasm-bindgen` methods.
`getDocumentInfo` / `get_document_info` returns the same preview JSON as
`DocumentCore::get_document_info`: its `version` is the `rjtd-model` package
version, not a file-format or stable schema version.

## Rust example

```rust,no_run
let bytes = std::fs::read("document.jtd")?;
let document = rjtd_wasm::JtdDocument::from_bytes(&bytes)?;
println!("{}", document.page_count());
# Ok::<(), Box<dyn std::error::Error>>(())
```

## Resource and interpretation limits

Construction rejects source input larger than 64 MiB and carries one mutable
`ResourceBudget` through byte parsing, `DocumentCore` page construction, and
the `JtdDocument` wrapper. Rust callers can supply custom `ParseLimits`; the
generated JavaScript constructor uses the default limits and converts
`ResourceLimit` failures to its error message. Canvas rendering is limited to
16,384 pixels per dimension and 64 MiPixels total. The binding uses
conservative fallback behavior for features not yet decoded by OpenJTD. A
`Candidate` is a provisional interpretation, `Unknown` is retained
unclassified data, and `Diagnostic` explains an incomplete interpretation.
Data marked `decoded: false` is therefore evidence, not authoritative layout
or style semantics. Browser behavior has been exercised with the repository
viewer, not every JavaScript framework or bundler.

## Compatibility API review

The repository viewer calls `free`, `pageCount`, `plainText`, `renderPageSvg`,
`renderPageSvgWithTextWidths`, `setFileName` and `setPrintDate`. Other methods are
still public Rust/wasm-bindgen SDK exports, so viewer non-use alone does not make
them safe to remove. Their current application/compatibility boundary is retained.
The class-name migration does not add editing or format support.

For example, `exportHwp` and `exportHwpx` remain unsupported empty-byte results;
`exportHwpVerify` reports an unimplemented-export error. Advanced form, object, table and property
operations may return documented defaults/no-op results. Do not infer source JTD
editing or round-trip support from those names. Deleting or changing an established
public method requires a separate consumer/API decision. No private unreferenced
compatibility implementation was found by the workspace lint and caller review.
